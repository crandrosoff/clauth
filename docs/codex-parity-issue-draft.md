## Codex parity: a follow-up series, offered for rulings before any PR

#69 landed the codex harness: the second roster, capture and browser login, `clauth start <codex>`, the usage poll, a separate chain, and a read-only Overview section. By `docs/codex-plan.md`'s parity map, everything else a Claude Code account gets — row actions, a Setup page, the chain editor, the Usage breakdown, the Config keys, the Tokens lens, `delegate` — stops at the harness line. `wiki/Codex.md` says it plainly: "the shell verbs above are the whole surface".

I use clauth with two codex workspaces beside four Claude accounts and would like to carry codex over that line, one slice per PR, each mergeable on its own. Before writing code I would rather have your rulings than guess. The full spec, in the style of `codex-plan.md`, is on my fork: **[docs/codex-parity-plan.md](https://github.com/crandrosoff/clauth/blob/docs/codex-parity-plan/docs/codex-parity-plan.md)**.

**Nothing here is implemented.** No branch, no PR. One slice had an implementation plan; an independent cross-model review falsified its design before any code was written, and the plan is marked withdrawn. That review is the reason this issue leads where it does.

### The one thing I want your ruling on first

**A running codex cannot be moved to a different account, and clauth should stop implying it can.**

My first draft of this series had a `follow_active` key: a codex switch would also repoint the operator's `~/.codex/auth.json` link, and a running `codex` would "adopt" the new account at its next token refresh. **That is wrong, on codex's own source.**

- `reload_if_account_id_matches` compares the reloaded `auth.json`'s account against the cached one. A different account fails that check, and `refresh_token` returns a permanent account-mismatch error rather than adopting it ([codex 0.155 `login/src/auth/manager.rs`](https://raw.githubusercontent.com/openai/codex/rust-v0.155.0/codex-rs/login/src/auth/manager.rs)). The ordinary cross-account switch already breaks, with no race needed.
- Worse, codex persists refreshed tokens **by path**. Repointing the link between a refresh request and its response can merge account A's replacement tokens into account B's store, leaving A holding a spent token ([0.145 `manager.rs`](https://raw.githubusercontent.com/openai/codex/rust-v0.145.0/codex-rs/login/src/auth/manager.rs), [`storage.rs`](https://raw.githubusercontent.com/openai/codex/rust-v0.145.0/codex-rs/login/src/auth/storage.rs)). An atomic rename of the *symlink* does not make the *read → network refresh → persist* transaction atomic.

So that design is withdrawn. **A2** replaces it and asks for a different thing entirely: an opt-in `codex` shim on `PATH`, generated by clauth, that starts the codex chain's active profile through `clauth start`. No link is repointed, no credential file is written, and no live adoption is claimed. A switch lands at **the next `codex` launch** — the same boundary `clauth start` already states when it refuses `--with-fallback`: *"codex reads auth.json once at start, so a chain lands at the NEXT start, not mid-session"*.

A related weakness the review found is **not** mine to fix and I am flagging it rather than touching it: `clauth_auth_store_owner` (`src/actions.rs:1573`) matches the `profiles/<name>/auth.json` **suffix** rather than membership under the real clauth root, so "a link elsewhere is left alone" is weaker than it reads.

### Preserved rulings, and the two amendments I am asking for

Most of #69's rulings are **preserved unchanged**: two rosters stay disjoint; the TUI calls the CLI's own codex writers; nothing reads a wire that does not exist (kick, spend ceiling, per-session fallback, keychain stay out); tabs learn a second list through one `RowSel { Claude(i) | Codex(i) }` selection type rather than a merged roster.

Two are **amendments I am requesting**, and I would rather name them than slip them in:

1. **`disable` / `enable` on a codex name.** Settled question 8 refuses these (`codex-plan.md:217`). Slice B wants them. Claude's `disable_profile` also refuses the active profile and a profile with a live session (`src/actions.rs:1638-1651`); the codex twin would carry both refusals in the same words.
2. **Launch-time account selection.** Decision 4's "a codex switch writes only `codex-profiles.toml`" is **unchanged** — A2 adds a separate launcher that reads the marker, it does not change what a switch writes.

### Slices, in order

- **A2. The `codex` shim** (opt-in, `codex_shim = false` by default): clauth generates a small `codex` program at `<data_dir>/clauth/bin/codex`, and the operator puts that directory on `PATH` themselves. It runs `clauth start <active-codex-profile> -- "$@"`. With no active profile it execs the real codex unchanged. Inside a clauth codex session it steps aside. Windows gets no shim, because `resolve_cli_command` prefers a native `.exe` over a `.cmd` (`src/runtime.rs:3570-3582`), so a `.cmd` shim would be found by a shell and skipped by clauth.
- **B. Overview + Setup:** codex rows selectable; actions `switch`, `re-login`, `delete`, reorder, plus `rename` and `disable`/`enable` if you take the amendment. Rename for codex has no existing writer — it must move roster, chain, marker, profile directory and any operator link together — so I am happy to split it and disable/enable into their own PR (R4b). A Setup page with only the rows a codex profile has, and a `+ codex login` row.
- **C. Fallback tab:** the codex chain editor (order, weekly line, `wrap_off`, `codex_shim`). Removing a member **preserves** the active marker, matching the claude editor (`remove_chain_member`, `src/tui/app.rs:6292-6304`) — `CodexState::remove_profile` clears it, but that is the delete-a-profile writer, not a chain-editing precedent.
- **D. Usage tab:** codex rows with the windows the wire reports, **labelled by their duration**, and a visible difference between "the wire reported no second window", "the poll has not run" and "the poll failed". Measured evidence, scoped honestly: **one rollout, one Pro account, 2026-09-19** reported `rate_limits.primary.window_minutes = 10080`, `secondary = null`. That is one sample from the **rollout** feed, and it does **not** by itself prove the empty `5h` cell is correct — that cell is fed by the `wham/usage` **poll**, which I have no fixture for. I would want one before claiming the dash is right.
- **E. Config tab:** the codex keys.
- **F. Tokens tab:** a codex cost lens fed from `rollout-*.jsonl` `event_msg/token_count` events. The roots matter: `clauth start` sessions write into `~/.clauth/profiles/<name>/codex-home/sessions`, not `~/.codex/sessions`, so scanning the operator home alone misses every session clauth itself launches. Rollouts in the operator home are **not** attributable to a profile — that directory can hold several accounts' history — so they land in an explicit `unattributed` bucket rather than being credited to whoever is active today. `--isolated` sessions are discarded at exit and are a stated coverage gap.
- **G. `delegate` over `codex exec`:** every delegate option is supported, translated, or **refused by name**. `allowed_tools` has no codex equivalent and is refused rather than silently dropped; `permission_mode` needs an explicit mapping onto `-s/--sandbox` before I would guess at one; `subagent_type` and `resume` are refused in this slice. The runtime guard, the env scrub and the `CLAUTH_MCP_DEPTH` recursion cap all carry over to the codex arm.
